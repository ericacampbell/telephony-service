# Transfer Brief

When a phone call is transferred, the receiving agent picks up cold. This service
gives them a brief first: who's calling, why, what's already been tried, what was
promised, how the caller sounds, risk flags, and the line to open with.

**Live:** https://telephony-service-753f.onrender.com (each tenant has its own
link; the token in the link is the credential)

```
audio ──▶ Groq whisper-large-v3-turbo ──▶ transcript ──▶ claude-sonnet-4-6 ──▶ brief
                                                          (JSON schema, Ajv-validated)
```

Measured on a 79-second recording: **~1s transcription, ~7s brief, ~8s end to end.**

## Three ways in, one pipeline

Every mode calls the same `runPipeline({ tenant, callId, audio, mode })`. The
Twilio routes and the upload endpoint are thin adapters over it.

| Mode | Entry point | State |
|---|---|---|
| **try-it** | `GET /t/:slug` — upload a recording in the browser | ✅ live |
| **intake** | `POST /voice/intake` — greet, record, brief, dial the agent with the brief whispered to them | ✅ built and tested, ⚠️ no phone number (see below) |
| **transfer** | agent → agent, dual-channel recording | ❌ not built |

### Why intake has no phone number

A Twilio **trial account cannot own a phone number** — confirmed against the API,
which reports `"incoming_phone_numbers": []`. The number the trial console shows
is Twilio's sandbox, so no webhook can be attached to it. The code path is
complete and unit-tested; it needs an upgraded Twilio account and one `curl` to
set `VoiceUrl`, not a code change.

## The brief

Generated by `claude-sonnet-4-6`. That model doesn't support
`output_config.format`, so the schema rides a **forced tool call** and is
validated with Ajv on our side: invalid → one retry with the validation errors
fed back → then a schema-valid fallback brief. **A bad brief never blocks a call
from bridging.**

```jsonc
{
  "caller": { "name": "string|null", "phone": "string|null", "account_ref": "string|null" },
  "reason": "string",                        // <= 200 chars
  "already_tried": ["string"],
  "promises": [{ "what": "string", "by_when": "string|null" }],
  "sentiment": { "label": "calm|frustrated|angry|distressed|neutral", "confidence": 0.0 },
  "risk_flags": ["churn|escalation|legal|vulnerable_customer|payment_dispute|none"],
  "first_line": "string",                    // <= 160 chars — what the agent says
  "confidence": 0.0,
  "unknowns": ["string"]                     // what the next agent still has to ask
}
```

Unknowns are `null` / `[]` / `"none"`, never invented — a hallucinated promise is
worse than an empty field, because the agent will repeat it to the customer.

## Multi-tenant

Several people demo at once, each against their own numbers, greeting, and data.
Every row carries `tenant_id` and every query filters on it.

Tenant resolution: inbound calls by the `To` number; the Try-it page by a
`share_token` accepted from the link path, `?k=`, an `X-Api-Token` header, or the
cookie the link sets on first load. One URL is the whole credential — share the
link, nothing else. Cross-tenant reads return **404, not 403**.

## Run it

```bash
npm install
cp .env.example .env          # add GROQ_API_KEY and ANTHROPIC_API_KEY
npm run fixture               # generate a sample call with macOS `say`
npm run pipeline -- --file fixtures/sample-call.wav --mode transfer
npm run dev                   # http://localhost:3000, link printed at boot
npm test                      # 24 tests, no API keys needed
```

Tests fake Groq, Anthropic, and Twilio at the client boundary, so the suite runs
offline and in CI.

## Persistence (built, not switched on)

Postgres is fully implemented — six tables, RLS enabled with no permissive
policy, forward-only migrations, `GET /calls/:id`. It activates on `DATABASE_URL`
alone:

```bash
npm run migrate
npm run seed-tenant -- --slug acme --name "Acme Ltd"
```

Without it, tenants come from a `TENANTS` env var (`scripts/make-tenants.js`
generates it) and nothing is stored — briefs live only in the response.

## Decisions worth knowing

- **Forced tool call, not structured outputs** — Sonnet 4.6 doesn't support
  `output_config.format`. One schema object feeds both the tool definition and Ajv.
- **`effort: medium`** — the brief is output-token-bound, so effort barely moves
  latency (6.97s vs 7.19s at low). Medium matches high for speed at lower cost.
- **The transcript is persisted before the model is called** — an LLM failure
  must not lose the call record.
- **Card and SSN digits are redacted before anything is stored or sent** —
  callers read them aloud.
- **Audio is never stored**, only the Twilio URL, transcript, and brief.
- **Twilio credentials are only ever sent to `*.twilio.com`** — a `RecordingUrl`
  arrives in an untrusted webhook payload.
- **Hold music must cover ~10s, not the ~6s first assumed** — measured, and the
  number grows with recording length.

## Scope choices

This was a two-hour build. The things that look thin are mostly deliberate:

- **One page, server-rendered, no framework or build step.** The UI exists to
  prove the pipeline, so it's a single HTML template served inline — no React, no
  bundler, no asset pipeline. That kept deploy to `npm ci && npm start` and meant
  a CSS fix was a one-line push rather than a rebuild. A real product needs an
  agent-facing view with call history and search; that's a different piece of work,
  not a bigger version of this page.
- **Deployed at stage 2, before persistence.** A live URL that does one thing
  beats a complete local service. It also surfaced two failures that never appear
  locally: a transitive dependency requiring Node 22, and Fastify not parsing
  form-encoded bodies (which would have broken every Twilio webhook).
- **In-memory fallback for tenants.** Lets the service run with no database at
  all, so the deploy never blocked on Supabase being ready.
- **No user accounts.** A token in a link is the whole credential. Right for a
  demo several people open; wrong for production, where agents need identities.
- **Brief generated synchronously while the caller holds.** Simple and fast
  enough (~8s) at this scale. A queue would be correct under real load.

## With more time

In the order I'd actually do them:

1. **Transfer mode** — the headline use case and the one that's missing. It needs
   dual-channel recording on leg one so "what the agent promised" and "what the
   caller tried" can be told apart by speaker, which is also what makes
   `already_tried` and `promises` reliable rather than plausible.
2. **Stream `first_line` first.** It's generated near the *end* of the JSON, so
   the whisper can't start until the whole brief finishes. Reordering the schema
   and streaming would cut several seconds of dead air on a live call — the
   difference between "brief before pickup" being comfortable and being tight.
3. **Turn persistence on** (it's written — `DATABASE_URL` and one migration) and
   add the agent-facing call history the schema already supports.
4. **An eval set for the prompt.** Right now prompt quality rests on one fixture.
   The `reason` field silently overran its 200-char cap on *every* run until I
   instrumented the retry path — a dozen labelled recordings with expected
   fields would have caught that immediately, and would catch the next
   regression.
5. **Expiring, rotatable tenant tokens.** Bearer credentials with no expiry are
   fine for an afternoon and not fine for a week.
6. **Speaker diarization** rather than relying on a single transcript stream, so
   attribution doesn't depend on the model inferring who said what.

## Known limitations

Transfer mode is not built. Tenant tokens are bearer credentials with no expiry.
Without `DATABASE_URL` nothing is stored, so `/calls/:id` is inactive. Intake has
no phone number on a Twilio trial account (above). The brief costs ~8s, so hold
music has to cover it.
